# Comment Hygiene v1.2.0

## Objective

Make the skill easier to install through established agent-skill tooling and
broaden regression coverage without weakening the explicit-review safety model.

This specification is proposed future work. Nothing in this document should be
read as shipped behavior.

## Skills ecosystem installation

- Research the current de facto skill package layout and installation contract,
  including the `npx skills` workflow, before selecting a distribution shape.
- Provide an installation path that uses the canonical public repository and does
  not require copying instructions by hand.
- Preserve one authoritative `SKILL.md`; packaging must not create drifting copies.
- Verify installation in a clean temporary environment and confirm that a
  compatible agent discovers the skill metadata and instructions.
- Document supported tooling precisely without implying universal compatibility.

### Installer and discovery contract

- Treat `skills/comment-hygiene/SKILL.md` as the canonical source layout unless
  research identifies a compatibility problem. It is a distributable source
  layout, not itself a project-discovery location for common coding agents.
- Record the exact installer version and command used to enumerate and install
  the skill, including the agent-specific target locations it creates.
- Establish a support matrix for Claude Code, Codex, Amp, and OpenCode from their
  primary documentation and observed installation results. A cell is supported
  only when both its path and discovery behavior have been verified; otherwise it
  must be documented as unverified rather than inferred.

### Portable execution boundary

- An installed skill must not assume that the target repository contains this
  repository's `Taskfile.yml`, `mise.toml`, or `scripts/comment-hygiene` wrapper.
- Select and implement one explicit runtime boundary for distributed use: bundled
  executable support files with declared prerequisites, or a separately installed
  public command. Keep source-repository usage working.
- Keep one authoritative `SKILL.md`; target-agent locations may be symlinks or
  installer-managed copies but must not become maintained instruction forks.

### Clean-environment verification

- In an isolated temporary home and target repository, install the canonical
  public source through the selected installer for every agent claimed supported.
- Verify the installed skill's frontmatter is discoverable by the relevant agent
  or its documented inspection command, then execute a read-only audit against a
  fixture from the installed skill path.
- Record installer version, source revision, exact commands, installed path,
  discovery evidence, runtime-prerequisite result, and cleanup behavior in a
  committed verification artifact or test output.

### Support documentation

- Document project-local and user-local installation commands separately, whether
  installation uses symlinks or copies, and how to update or remove it.
- State the tested agent versions and scope. Do not say that all `SKILL.md`
  consumers or all agent versions are compatible.
- Explain direct clone use and the distributed runtime prerequisite without
  requiring users to copy instructions by hand.

## Expanded behavioral coverage

- Prove that `audit` and `audit-all` do not mutate their inputs.
- Cover `audit-all` and `strip-all` handling of documentation, TODO, and FIXME
  comments independently from ordinary-comment behavior.
- Prove URL-like string data remains unchanged in ordinary and broad modes.
- Cover recognized lint/formatter directives and standalone or trailing comments
  protected with `~keep`.
- Keep fixtures separated by policy so regressions identify the changed behavior.

## Compatibility and rollout

- Keep the v1.0 command names and explicit-apply contract backward compatible.
- Pin and test dependency upgrades before changing the supported syntax behavior.
- Treat a packaging channel as additive; direct repository use must continue to
  work.

## Acceptance criteria

1. The selected skill installer succeeds in a clean environment using documented
   commands and the installed skill is discoverable.
2. CI covers ordinary, broad, protected-comment, and string-data fixtures.
3. Existing v1.0 commands and safety behavior remain unchanged.
4. Documentation distinguishes verified integrations from proposed ones.

## Explicitly out of scope

- Publishing before the package/discovery contract has been researched and tested.
- Automatic semantic classification or prose rewriting.
- Removing comments across an entire repository without scoped authorization.
